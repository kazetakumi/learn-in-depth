C, from zero to architect · Rung 0

Nothing is running your program

Here is a complete C program. Six lines. Put it in a file called hello.c.

#include <stdio.h>

int main(void) {
    printf("hi\n");
    return 0;
}

Two commands and it runs:

$ cc hello.c -o hello
$ ./hello
hi

Good. Now I want to spoil it for you, because there is a question buried in those two commands that most people never ask, and everything else in this course depends on the answer.

You wrote 73 bytes of text. The file hello that came out is 33,432 bytes. Something added 33 kilobytes of material you did not write. And you called a function named printf — where did that come from? It isn't in your file. You never defined it. You never wrote a single instruction telling the machine how to put letters on a screen.

So what exactly happened between those two commands?

The model you already haveSource code goes in, a program comes out

If you've encountered any explanation of this before, it looked like this:

hello.c  ──[ compile ]──▶  hello

One arrow. You write source code, the compiler turns it into an executable, you run the executable. It isn't wrong, exactly. It's the picture you get from across the room. But it's one arrow where there are four, and every interesting thing that will ever go wrong for you lives in the joints between them.

We're going to take the arrow apart. Not by me telling you the four stages — that would be a list, and lists evaporate. Instead we'll stop the machine at each stage and read what it produced. You'll predict first, then look. Predict badly; that's the point. The gap between what you expected and what you see is the only thing that actually installs a model.

Stage oneThe preprocessor: before C, there is text

The first stage is called the preprocessor, and you can stop the machine right after it with cc -E. It prints, instead of compiling.

Predict before you run it

Your file is 6 lines long. cc -E hello.c prints the text after the first stage has finished with it. How many lines come out?

Commit to a number. Say it out loud. Then run it.

What actually comes out 
$ cc -E hello.c | wc -l
     572

Five hundred and seventy-two lines. And here are the last few:

$ cc -E hello.c | tail -6
# 2 "hello.c" 2

int main(void) {
    printf("hi\n");
    return 0;
}

Your six lines are at the bottom, untouched. The other 566 are new. They all came from a single line of yours: #include <stdio.h>.

So #include brought 566 lines of something into your file. The obvious guess is that it imported the printing machinery — that stdio.h contains the code for printf and #include fetched it.

That guess is wrong, and it's worth breaking properly, because #include is much dumber and much stranger than an import.

Try this one

Make a file called frag.h containing exactly this — yes, an unfinished line, no closing brace, nothing valid:

int main(void) { return

And a file weird.c containing exactly this:

#include "frag.h"
 7; }

Neither file is a legal C program. Neither one contains a complete function. What happens when you run cc weird.c -o weird?

What happens 
$ cc weird.c -o weird
$ ./weird
$ echo $?
7

It compiles. It runs. It exits with status 7.

Status 7? When a program finishes, it hands one small number back to whatever started it. That number is what your main returns — which is why every program so far has ended with return 0, zero meaning "nothing went wrong". The shell keeps the last one in $?, so echo $? asks it. Here main returned 7, so 7 came back. Worth noticing on this rung in particular: that return value is not caught by any runtime — it is handed to the operating system, which is the only thing still around once your program ends.

Because #include "frag.h" does exactly one thing: it takes the text of frag.h and pastes it in, character for character, where the #include line was. After the paste, the compiler sees a single stream of text that happens to read:

int main(void) { return
 7; }

which is a perfectly ordinary C program that returns 7.

Sit with that for a second, because it's the whole lesson in miniature. #include is not an import. It does not understand modules, functions, or namespaces. It is a copy-paste that happens before anyone checks whether your program is C. That's why the stage is called the pre-processor: it runs first, and it does not speak the language.

Where the name comes from

Every line beginning with # is an instruction to this stage, not to the compiler — which is why they don't end in semicolons and don't follow C's grammar. They're a small, separate language for shuffling text around, bolted onto the front. In rung 14 you'll see how much of large-scale C architecture is built out of this one crude tool, and what it costs.

Still stage oneSo what did those 566 lines give you?

If stdio.h isn't the code for printf, what's in it? Let's look for the line that mentions printf:

$ cc -E hello.c | grep -n "int printf"
316:int printf(const char * restrict, ...);

(That line carries a trailing compiler attribute in the real output; I've trimmed it here. Everything else is verbatim.)

One line. Not a body, not a block of instructions — no { anywhere. Just a sentence that says: there exists a thing called printf, it takes a piece of text and then any number of other arguments, and it hands back an int.

That is called a declaration. It describes a shape without providing the substance.

Think about this before reading on

The compiler is about to translate printf("hi\n") into machine instructions. It has been given only that one-line description — the shape of printf, not its code. Why is that enough? What does a translator actually need to know in order to write down "call this function"?

The answer, and it's the hinge of the whole lesson

To generate a call, the compiler needs to know where to put the arguments and where the answer will come back. That's it. It does not need to know what the function does.

Which means the compiler can translate your call to printf while remaining completely ignorant of whether printf exists anywhere in the universe. It writes down the equivalent of "put this address in the first argument slot, then jump to whatever printf turns out to be" — and moves on.

Somebody, later, has to make that jump land somewhere real. Hold onto that thought. It's stage four.

Stage twoThe compiler: C becomes instructions

Now the actual compiler runs. Its input is those 572 lines of pure C text; its output is assembly — the human-readable spelling of the machine's own instruction set. Stop the machine here with cc -S.

Careful — this one is silent

Unlike -E, the flag -S does not print. It writes a file called hello.s and says nothing at all, which looks exactly like failure. It isn't: in Unix, silence means success.

So either look at the file it wrote, or ask for the terminal explicitly — -o - means "send the output to standard output":

$ cc -S -O0 hello.c        # writes hello.s, prints nothing
$ cat hello.s              # ...so look at it

$ cc -S -O0 hello.c -o -   # or print it straight to the screen

The -O0 switches the optimiser off, so the assembly still corresponds to your source line by line. Turn it up later and watch how much of your code the compiler simply deletes.

Your computer has an Apple M-series chip, so the instructions are ARM64. Here is the whole of main, with the ceremony trimmed:

_main:
    sub     sp, sp, #32           ; take 32 bytes of scratch space
    stp     x29, x30, [sp, #16]   ; save where to return to
    add     x29, sp, #16
    mov     w8, #0
    str     w8, [sp, #8]
    stur    wzr, [x29, #-4]
    adrp    x0, l_.str@PAGE       ; put the address of our text
    add     x0, x0, l_.str@PAGEOFF  ;   into argument slot 0
    bl      _printf               ; branch-and-link to printf
    ldr     w0, [sp, #8]          ; the value we return: 0
    ldp     x29, x30, [sp, #16]   ; restore where to return to
    add     sp, sp, #32           ; give back the scratch space
    ret

l_.str:
    .asciz  "hi\n"                ; our string, now sitting in the file as data

You are not expected to read ARM64 assembly yet. Look at exactly two things.

First, at the bottom: l_.str: .asciz "hi\n". Your string has stopped being part of a statement and become data — a labelled run of bytes that will sit in the finished file. The two instructions adrp/add above it compute the address of those bytes and put it in x0, the first-argument slot.

Second, and this is the one that matters: bl _printf. Branch-and-link — jump to _printf, remembering how to get back. The compiler has written down a jump to a place it cannot name. It has no idea where printf is. It has never seen a single instruction of it. It wrote the jump anyway, because the declaration told it the shape, and the shape was all it needed.

That instruction is a promise, made on your behalf, that someone else will have to keep.

Stage threeThe assembler: text becomes bytes

Assembly is still text. The third stage, the assembler, turns each instruction into the actual numbers the processor executes. Stop here with cc -c, which produces an object file.

$ cc -c hello.c -o hello.o
$ file hello.o
hello.o: Mach-O 64-bit object arm64

Not text any more. If you open it in an editor you'll get garbage. But it is not shapeless garbage — it keeps a list of names, and you can read that list with nm:

$ nm hello.o
0000000000000000 T _main
                 U _printf

Two letters carry the entire meaning here.

T means text — this file has that thing. Here are the bytes of _main, at offset zero.

U means undefined — this file needs that thing and does not have it. Notice there's no address next to _printf. That column is blank because there is nothing to point at.

That single U is the reason a fourth stage has to exist.

The testDoes the compiler check whether anything exists?

Before we go on, let's test the claim I made earlier — that the compiler translates your calls while remaining ignorant of whether the functions are real.

Predict

Here is ghost.c. It declares a function called wibble and calls it. wibble does not exist. Not in this file, not in any library, not anywhere on your machine — I invented the name.

int wibble(int);

int main(void) {
    return wibble(3);
}

Does cc -c ghost.c succeed or fail? Decide before you look.

Run it and see 
$ cc -c ghost.c -o ghost.o
$ echo $?
0
$ nm ghost.o
0000000000000000 T _main
                 U _wibble

Clean success. No error, no warning. The compiler produced a perfectly valid object file containing a jump to a function that has never existed.

Now compile and link:

$ cc ghost.c -o ghost
Undefined symbols for architecture arm64:
  "_wibble", referenced from:
      _main in ghost.o
ld: symbol(s) not found for architecture arm64

The failure arrives one stage later, and from a different program — ld, not the compiler.

So the compiler never checks whether anything exists. It checks only that you declared a shape, and then trusts you completely. All it leaves behind is a U — a recorded debt: this file needs a thing it does not have.

Why this is worth remembering

"Undefined symbol" is one of the two or three error messages you will see most often for the rest of your life in C, and it confuses people for years because it doesn't look like a normal compile error. Now you know exactly what it means: somebody promised me this thing existed, and it does not. Not a typo in your syntax — an unkept promise. It's the last stage complaining about something the first stage let through.

Stage fourThe linker: keeping the promises

The final stage is the linker. Its job is to take every U in every object file and find something to point it at.

Let's watch it fail first, by calling the linker directly on our object file with nothing else:

$ ld hello.o -o broken
Undefined symbols for architecture arm64:
  "_printf", referenced from:
      _main in hello.o

Confirmed: the code for printf was never in your file, and never in stdio.h either. All stdio.h gave you was the promise. The code lives somewhere else entirely — in a system library that was compiled long before you sat down, shipped with your operating system. When you run cc hello.c -o hello, the compiler driver quietly hands that library to the linker on your behalf, the U gets resolved, and the jump finally lands somewhere real.

The point of all of itNow: what is running your program?

Go back to the opening question. You type ./hello and text appears. What is interpreting your program while it runs?

Nothing. There is nothing there.

The operating system opens that 33-kilobyte file, copies its bytes into memory, and jumps to the entry point recorded inside it. From that instant the CPU is executing your bytes directly. No supervisor, no translator, no runtime. The four stages were a preparation that finished before your program began, and once it began, everything that knew anything about C had already exited.

Compare that with the other way of doing it. When you run python hello.py, the thing that starts is python — a large program (written in C, as it happens) that reads your text and acts on it, staying there the whole time your program runs, holding your variables, checking your types, catching your mistakes, cleaning up after you. Your Python program never touches the processor. It asks python to do things.

C has no such attendant. And this single fact generates almost everything else you will learn. C is fast because there is no intermediary. C lets you index past the end of an array because there is no one there to object. Your program crashes with a segmentation fault rather than a helpful error message because a segmentation fault is the hardware complaining — the last line of defence, and the only one, since nothing softer is watching.

Every rung above this one is a consequence of the room being empty.

Why anyone wanted thisA language for moving an operating system

It's worth knowing why this design exists, because it wasn't an accident and it wasn't ideology.

At the start of the 1970s, an operating system was written in the assembly language of one specific machine. That was simply what an operating system was. And it meant that when the machine was replaced — as it always was — the operating system did not move. You wrote it again. Years of work, thrown away, for the new instruction set.

A small group at Bell Labs had built a system called Unix on a modest machine and wanted it on the next one without starting over. The way out was to invent a notation sitting just above assembly: close enough to the hardware that it translated into tight machine code with no support structure underneath, but abstract enough that it wasn't about one machine's instruction set. Then you write the operating system in the notation, and to move it you re-translate rather than rewrite.

That notation is C, and it worked — Unix moved, and the descendants of that decision are running on your phone. But look at the constraint that produced it: it must translate into fast machine code with nothing underneath. No runtime, no bookkeeping, no invisible helper. When you meet something in C that looks hostile — that arrays don't know their own length, that strings are a convention rather than a type, that nobody stops you writing past the end of anything — the design is not being careless. It is refusing to put a runtime in the room, because the runtime was the thing it was invented to do without.

Your turnPredict the whole pipeline, cold

Reading this felt like understanding. It isn't yet. Do this before you go on, and write your predictions down before running anything — a prediction you didn't commit to is a prediction you can't be wrong about, and being wrong is the part that teaches.

Make two files.

/* greet.c */
#include <stdio.h>

void greet(const char *who) {
    printf("hello, %s\n", who);
}
/* main.c */
void greet(const char *who);

int main(void) {
    greet("world");
    return 0;
}

Notice that main.c does not #include anything. It declares greet by hand — the shape, nothing else.

1. Roughly how many lines will cc -E main.c produce, and why is that number so different from cc -E greet.c?

2. Will cc -c main.c succeed, given that the code for greet is in a different file it has never seen?

3. What will nm main.o show — which names are T, which are U? Now the same for nm greet.o.

4. What does cc main.o -o app do, with greet.o left out? Write the error you expect, in your own words, before you see the real one.

5. Now build it properly with cc main.c greet.c -o app. Which stage was it that finally connected the two files — and what would have happened if you had misspelled the declaration in main.c as void greet(int); instead?

Check yourself — but only after you've written all five down

1. main.c gives 13 lines; greet.c gives 571. main.c has no #include, so the preprocessor has nothing to paste and the output is barely longer than the input. greet.c balloons because stdio.h drags in the declarations of the entire standard I/O interface — for the sake of the one line that describes printf.

2. Yes. Compiling never checks existence — only that a shape was declared. It emits a jump and records the debt as a U.

3. main.o: T _main, U _greet. greet.o: T _greet, U _printf. Each file has one thing and owes another. The linker's job is to notice that one file's U is another file's T.

4. Undefined symbol _greet, referenced from _main. Same failure as wibble, and for the same reason — the promise was never kept.

5. The linker, and only the linker. As for the mismatched declaration — try it, because the result is worth seeing:

$ cc bad.c greet.c -o badapp
$ echo $?
0                       ← compiled and linked, no complaint at all
$ ./badapp
$ echo $?
139                     ← 128 + 11: killed by signal 11, segmentation fault

It builds perfectly, because the linker matches on the name _greet and nothing else. It never checks that the shape you promised matches the shape that exists. So your program hands the number 42 to a function expecting an address, printf goes looking for text at address 42, and the hardware kills the process.

No one warned you at any stage. That is the empty room, and you just felt it for the first time. Closing this particular hole is what header files are for — rung 14.

Before you move on. This lesson read smoothly, and smooth reading produces a warm feeling that is easy to mistake for understanding. It isn't. The test is whether you can do this cold, tomorrow, without the page: draw the four stages, name what enters and leaves each one, and explain — without looking — why ghost.c compiles but doesn't link. If you can't, you haven't lost anything; you've just found out that reading and knowing are different, which is the most useful thing this rung can teach you.

The compiler

cc C compiler

The traditional Unix name for "whichever C compiler this machine has". On your Mac it is Apple's clang; on a Linux box it would usually be gcc. The name is a stable label so that build instructions written in 1980 still work today.

$ cc --version
Apple clang version 21.0.0
Target: arm64-apple-darwin25.3.0

But cc is not the compiler. It's a driver — a small program that runs the four stages in order and passes each one's output to the next. Watch it narrate with cc -v. It also quietly hands the system library to the linker on your behalf, which is why cc hello.c -o hello succeeds where calling ld alone fails.

Its flags

The stage flags are all the same idea: where to stop.

   -E ──┐    -S ──┐    -c ──┐    (no flag) ──┐
        ▼         ▼         ▼                ▼
  preprocess → compile → assemble  →       link
-Estop after preprocessing. Prints to the terminal
-Sstop after compiling. Writes name.s and prints nothing
-cstop after assembling. Writes name.o and prints nothing
-o Foutput to file F. -o - means "to the terminal"
-O0Optimisation level zero — off. Keeps assembly matching your source
-gkeep debugging information, so a debugger can show your variable names
-Wall -Wextraturn on warnings. Use these always

Do these letters stand for words? Mostly no. The manual gives no expansions — they're conventional single letters inherited from 1970s Unix, chosen to be short to type. Only -o (output) and -O (optimisation) genuinely abbreviate anything. Expand, Source to aSsembly and compile only are memory aids, not etymology.

Two that catch people

-o and -O differ only in capitalisation and do completely different jobs. Lowercase names the output file; uppercase sets optimisation.

-S is silent. It writes hello.s and says nothing, which looks like failure. Use cat hello.s to read it, or cc -S -O0 hello.c -o - to print it straight to the screen.

The shell

echo $? print the last exit status

Two things joined. echo prints its arguments. $? is a variable the shell keeps holding the exit status of the last command that finished.

Every program that ends hands back one small integer. Zero means success; anything else means some kind of failure. That's backwards from "zero is false", and it makes sense: there's one way to be fine and many ways to fail, so zero is reserved and the rest are free to distinguish problems.

$ ./three          # a program whose main does: return 3;
$ echo $?
3

$ ls nosuchfile    # a command that failed
$ echo $?
1

That number is what your main returns. It's why main is declared int and why every program ends with return 0 — you've been reporting success to the operating system all along.

One special range: values above 128 mean the program didn't exit at all, it was killed. Subtract 128 to get the signal number.

139128 + 11 — signal 11 is SIGSEGV, a segmentation fault
134128 + 6 — SIGABRT, usually a failed assert
130128 + 2 — SIGINT, you pressed Ctrl-C

The pipe |

Takes what the left-hand program writes out and feeds it directly into the right-hand program as input, with no file in between.

$ cc -E hello.c | wc -l
572

Neither program knows about the other. That independence is the whole point of the design, and it's the subject of rung 19.

wc word count

Counts things in text. With no flags it prints lines, words and bytes together.

wc -llines
wc -wwords
wc -cbytes

grep globally search a regular expression and print

Prints the lines of its input that match a pattern. The peculiar name is from an old editor command, g/re/p. Nobody would choose it today; it stuck.

-ccount matches instead of printing them
-iignore case
-wwhole word only — pointer won't match pointers
-nshow line numbers
-rsearch a whole directory tree
-lprint only the filenames that matched
-vinvert — print the lines that don't match
-oprint only the matching part, not the whole line
-A2 -B2also show 2 lines after / before each match

-o is the underused one — it turns grep into a counting instrument when chained with others:

$ grep -o "cc -[EScv]*" lesson.html | sort | uniq -c | sort -rn
   7 cc -E
   5 cc -c
   1 cc -S

The pattern is a regular expression, not just a word. Add -E for the fuller syntax and use it by default.

^ $start of line, end of line
.any single character
* + ?previous thing: zero-or-more, one-or-more, optional
[abc]any one of these
[^abc]any one except these
|or — grep -E "malloc|free"
\take the next character literally
$ grep -E "^\[0:[0-5][0-9]:.*compil" transcript.txt
    ^      start of line
     \[    a literal [
       0:  hour must be 0
          [0-5][0-9]   minutes 00-59
                    .* anything
                      compil

This matters beyond convenience: it is how you will read source code. When you open a project with hundreds of thousands of lines you don't read it front to back, you ask it questions — grep -rn "struct sds" . for where something is defined, grep -rn "sdsnew(" . for who calls it.

Looking inside compiled files

nm names

Lists the symbols — the names — recorded inside a compiled file. You can't read an object file, but it isn't shapeless: alongside the machine bytes it keeps a table of names, and nm prints that table.

$ nm hello.o
0000000000000000 T _main
                 U _printf
Ttext — this file has it, at that offset
Uundefined — this file needs it and doesn't have it
D Binitialised data / uninitialised data (rung 8)
lowercaselocal to this file; uppercase means visible to the linker
nm -ushow only the undefined ones — usually the question you have

Note the blank address column on the U line. There's nothing to point at; that blank is the recorded debt. Reading two object files together shows you the linker's entire job:

$ nm greet.o          $ nm main.o
T _greet              U _greet
U _printf             T _main

One file's U is the other file's T. Matching those up is all linking is.

The leading underscore on _main is a macOS convention — the toolchain prepends one to every C name. On Linux you'd see plain main. Nothing deep.

The habit: when a build fails with "undefined symbol", run nm on your object files. It turns "something is wrong somewhere" into "this file wants this exact name and nobody provides it".

file

Tells you what kind of thing a file is, by inspecting its contents rather than trusting its name.

$ file hello.o
hello.o: Mach-O 64-bit object arm64

Words

Jargon and English idioms used in the lessons, in case any of them are new.

symbola name recorded in a compiled file — a function or a global variable
object filethe .o output of the assembler: machine code plus a symbol table, not yet a program
drivera program whose job is to run other programs in the right order. cc is one
little-endianstoring the least significant byte at the lowest address, so 1 is 01 00 00 00
segfaultshort for segmentation fault — the hardware killing your program for touching memory it has no right to
IOUEnglish idiom, said as "I owe you": a note acknowledging a debt to be settled later. Used for the U a compiler leaves behind. Since replaced in the lesson with plainer wording
ceremonyinformal: the boilerplate parts of code or output that carry no meaning for the point being made
to bite youEnglish idiom: to cause a problem later, usually one you were warned about
Silence is success

A habit of mind worth forming early: when a Unix command succeeds, it says nothing. cc hello.c -o hello printing nothing means it worked perfectly. Tools only speak up when something is wrong — the same philosophy as exit status 0.

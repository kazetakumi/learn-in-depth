C, from zero to architect · Rung 1

Memory is one long street; a type is a pair of glasses

Here are four bytes. I got them out of my computer's memory a moment ago, and I've written each one in hexadecimal:

db  0f  49  40

My question is simple, and it has no trick in it. What number is that?

Take a moment with it, because the answer is going to reorganise how you think about every variable you will ever declare.

Two answersBoth correct. Neither is more correct.

Here is a program that puts those four bytes into memory once, and then reads the same four bytes twice — first through an int, then through a float. Nothing is converted. Nothing is recomputed. The bytes are not touched between the two readings.

#include <stdio.h>
#include <string.h>

int main(void) {
    int   i = 1078530011;
    float f;
    memcpy(&f, &i, 4);        /* copy the four bytes, unchanged */

    printf("as int:   %d\n", i);
    printf("as float: %f\n", f);
    return 0;
}
$ cc -Wall reinterpret.c -o reinterpret && ./reinterpret
as int:   1078530011
as float: 3.141593

One thousand and seventy-eight million. And also π. The same four bytes.

So the honest answer to "what number is that?" is: the bytes do not know. They are not a number at all. They are a pattern of on and off, and a number is what you get when somebody decides how to read them.

The question that followsThen who remembers what type it was?

This is where the previous rung pays for itself, so let's use it.

You established last time that once your program is running, nothing is there. The compiler translated your text into machine bytes and exited. No interpreter, no supervisor, no runtime is present while your program executes.

Reason it through before reading on

Nothing is watching at runtime. Memory holds nothing but bytes. So when your program is halfway through running and there is a variable sitting in memory — where is the information that it's an int rather than a float?

Which part of the machine is holding onto that fact?

The answer, and it is the crux of this rung

Nowhere. Nothing is holding onto it. The information is gone.

The type existed in one place only: the compiler's notes, during translation. The compiler used it to decide how many bytes to set aside and which machine instructions to emit — integer addition or floating-point addition, a 4-byte load or an 8-byte load. Then it wrote those instructions down and exited, and the type went with it.

What survives into the running program is bytes and instructions. Not one bit of memory anywhere records "these four bytes are an int."

So here is the sentence to carry out of this rung:

A type is not a property of the bytes. It is a lens — an instruction to the compiler about how many bytes to take and how to read them.

Every confusing thing in this lesson, and a surprising number in the rest of the course, is a consequence of that one sentence. When two lenses disagree about the same bytes, C does not stop you. There is nobody there to stop you.

Build the instrumentYou cannot study what you cannot see

From here on, the subject of this course is invisible. Bytes in memory have no appearance. So before we go further, we build something to look at them — about eight lines, and you will use it for the rest of your life in C.

#include <stdio.h>

void dump(const char *label, const void *p, size_t n) {
    const unsigned char *b = p;
    printf("%-22s", label);
    for (size_t i = 0; i < n; i++)
        printf("%02x ", b[i]);
    printf("\n");
}

Don't worry about const void * or the cast — that's rungs 4 and 5, and the function will still work while you don't understand its signature. What it does is the point: given the location of anything at all, print n bytes starting there, in hexadecimal. It doesn't care what type you thought you had. It reads raw.

Now put it to work.

Predict — and be specific

We store the integer 1 in an int, which occupies four bytes, and dump all four.

int one = 1;
dump("int 1:", &one, 4);

Write down the four bytes you expect to see, in order, before you run it.

What actually comes out 
int 1:                01 00 00 00

If you predicted 00 00 00 01 — the way you'd write the number on paper, with the small end last — you predicted the same thing almost everyone does, and you were wrong in an interesting way.

The surpriseThe small end comes first

Your machine stores the least significant byte at the lowest address. The number one is 01 followed by three zeros, not three zeros followed by 01. This is called little-endian ordering, and it is what your Mac, and essentially every desktop and phone processor you will meet, does.

It looks backwards, and it isn't arbitrary. Consider what it buys you.

Suppose you have an 8-byte number sitting at some address, and you want to read just its bottom four bytes as a smaller integer. On a little-endian machine, the bottom four bytes are the first four bytes — you read from the same address, you just take fewer. Nothing moves. On a big-endian machine you'd have to start four bytes further along. Arithmetic likes it for the same reason: addition carries from the small end upward, so processing memory in increasing address order processes the number in the order the carry travels.

Where this will bite you

Little-endian is a choice your processor made, not a law. Network protocols settled on the opposite order — which is why it's called network byte order — so the moment you send a number over a socket or write it into a file that another machine will read, the two ends disagree about which byte comes first. That's rung 20, and this is why it exists.

Look back at the four bytes at the top of this lesson: db 0f 49 40. Written the way a human would, most-significant first, that's 0x40490fdb — the number 1078530011. You were reading it backwards the whole time.

How wide is each lenssizeof

If a type says how many bytes to take, you should be able to ask how many. The operator is sizeof, and it answers in bytes. On your machine:

char         1   short        2
int          4   long         8
long long    8   float        4
double       8   void *       8

Two things worth noticing.

First, sizeof is not a function. It's resolved during translation — by the time your program runs, sizeof(int) has already been replaced by the constant 4. Which follows from the crux: the size is part of the lens, and lenses live at compile time.

Second, and this is the one that matters for an architect: these numbers are not guaranteed. The standard promises almost nothing — that char is 1, and that the sequence short ≤ int ≤ long ≤ long long never decreases. That's close to all. An int is 4 bytes here; it has been 2 on machines that shipped in enormous numbers, and long is 8 here but 4 on Windows today.

Think like an architect for a moment

You're writing a program that saves data to a file, and another program — possibly on a different kind of computer — will read that file back. You need a field that is exactly 32 bits wide, on every machine, forever.

Can you write that with int? If not, what would you want the language to give you?

What you want, and it exists

You cannot use int, because int means "whatever this machine finds natural," and that is exactly the wrong promise. What you want is a type that names the width instead of the machine. Include <stdint.h> and you get precisely that:

#include <stdint.h>

int32_t   count;     /* exactly 32 bits, signed */
uint8_t   flags;     /* exactly 8 bits, unsigned */
uint64_t  offset;    /* exactly 64 bits, unsigned */

The rule that follows: use int when the number is just a number — a loop counter, a size you'll never store. Use the fixed-width types the moment the bytes leave your program — a file, a network packet, a hardware register. Anywhere the layout is part of an agreement with someone else.

These arrived in 1999, two decades after C was designed, which is why older code you read is full of int where it should not be. Now you'll notice.

A lens you didn't know was a lensThere is no character type

You've been writing char since your first program. Let's find out what it is.

char a = 'A';
printf("'A' as a number: %d\n", a);
printf("'A' + 1 as a character: %c\n", a + 1);
printf("'z' - 'a' = %d\n", 'z' - 'a');
Predict all three lines

Does the first one even compile? Can you add 1 to a letter? Can you subtract one letter from another?

All three run, and here is what they print 
'A' as a number: 65
'A' + 1 as a character: B
'z' - 'a' = 25

char is a one-byte integer. That's all it has ever been. 'A' is not a letter — it is a way of writing the number 65 that reads better than 65 does. The dump confirms it:

char 'A':             41

0x41 is 65.

So %d and %c are not conversions. They are two lenses on the same byte: show me this as a number, or show me the letter this number stands for. The mapping from 65 to "A" is a convention called ASCII, agreed in the 1960s, and it lives in the printing code — not in the byte.

This explains a family of things at once. Why 'z' - 'a' gives 25: the letters were assigned consecutive numbers, so subtracting them gives a distance. Why c - '0' turns the character '7' into the number 7. Why sorting strings puts all capitals before all lowercase — capitals were given the smaller numbers. None of that is a rule to memorise. It all falls out of letters are numbers, and the ordering was chosen sensibly.

The street has wallsWhat happens at the end

A byte holds 256 patterns. An unsigned char reads those as 0 to 255. So:

Predict 
unsigned char u = 255;
u = u + 1;
printf("%u\n", u);

What prints? There is no error handling here and no check. Given what you know about who is watching at runtime, what can this possibly do?

What happens 
unsigned char 255 + 1 = 0

It wraps to zero, silently. Nothing is raised, nothing is logged, nothing notices.

And you could have predicted it from rung 0. There is no runtime present to check the result, and adding a check to every arithmetic operation is exactly the cost C was invented to avoid. So the hardware does what hardware does — it computes 256, which needs nine bits, and only eight fit. The ninth is discarded. Zero remains.

For unsigned types this wraparound is defined and guaranteed: it's arithmetic modulo 256. For signed types, overflow is something worse than wrong — and that is rung 3.

The trapWhere two lenses meet

One more, and it is the one that catches professionals. Read this carefully; there is nothing hidden.

int n = -1;

if (n < sizeof(int))
    printf("true\n");
else
    printf("false\n");
Commit to an answer

n is −1. sizeof(int) is 4. Is −1 less than 4?

Does this print true or false?

Run it 
-1 < sizeof(int)  -> FALSE
   because -1 converted to unsigned is 4294967295

Minus one is not less than four.

Here is why. sizeof produces an unsigned value — it's a count of bytes and cannot be negative. When C compares a signed value with an unsigned one, it does not refuse, and it does not warn by default. It converts one to match the other, and the rule is that the signed one becomes unsigned.

So before comparing, −1 is reinterpreted through the unsigned lens. The bit pattern of −1 is all ones, and all ones read as unsigned is 4,294,967,295 — the largest 32-bit value there is. The comparison being made is not "is −1 less than 4". It is "is 4,294,967,295 less than 4".

The bytes never changed. Only the lens did.

Two habits, starting now

Compile with -Wall -Wextra. The compiler can see this one coming and will tell you — but only if you ask. C's default posture is silence.

Be suspicious whenever a signed and an unsigned value meet. The classic form of this bug is a loop that counts down: for (unsigned i = n; i >= 0; i--) never ends, because an unsigned value is always greater than or equal to zero. It wraps to four billion instead of going negative.

Your turnMake the invisible visible

Build the dump function into a file of your own, and use it to answer these. Write your prediction down first, every time — the value is entirely in the gap between what you expect and what appears.

1. Dump a double holding 3.14159, all 8 bytes. Then dump a float holding the same value, all 4. Do the float's bytes appear anywhere inside the double's? Should they?

2. Dump the int value 1, then 256, then 65536. Explain the pattern you see in one sentence, using the word little-endian.

3. Dump a short holding -1, then an unsigned short holding 65535. Compare the bytes. What does this tell you about what "negative" means to the machine?

4. Predict, then check: what does printf("%d\n", 'A' + 'B'); print, and why is that not a nonsense question?

5. This one is the architect's question. You're designing a file format. It needs a field for "number of records", and you're confident there will never be more than a few thousand. A colleague writes int count;. Give two distinct reasons that is the wrong choice, and write the line you'd use instead.

Check yourself — after all five are written down

1. No.

double 3.14159 (8):     6e 86 1b f0 f9 21 09 40
float  3.14159 (4):     d0 0f 49 40

A double is not a float with extra bytes bolted on — the two use different layouts, so the shorter pattern doesn't sit inside the longer one. Both encode roughly 3.14159, differently. That's rung 2.

One thing worth catching if you noticed it: the float here is d0 0f 49 40, while the four bytes I opened the lesson with were db 0f 49 40. Nearly the same, not identical — and both print as 3.141593. Two different byte patterns displaying as the same number is your first hint that a float does not hold the value you typed. It holds the nearest one it can. Also rung 2.

2. 01 00 00 00, then 00 01 00 00, then 00 00 01 00. Multiplying by 256 shifts the 01 one byte to the right, because little-endian puts the least significant byte at the lowest address and each successive byte is worth 256 times the last.

3. Identical: ff ff. −1 and 65535 are the same bits. "Negative" is not a property of the bytes — it's the lens. The signed lens reads the top bit as a sign; the unsigned lens reads it as just another digit. Which is this rung's crux appearing again, in the place it does the most damage.

4. It prints 131. Not nonsense at all: 'A' is 65 and 'B' is 66, both are integers, and 65 + 66 = 131. The oddity isn't that it works — it's that you ever thought of them as letters.

5. Two reasons. Width: int is whatever the compiler chooses — 4 bytes here, possibly 2 elsewhere — so a file written on one machine may be unreadable on another, and the format has no fixed definition. Signedness: a count cannot be negative, so a signed type throws away half its range and invites exactly the comparison trap you met above. Write uint32_t count; — and now the file format is specified by the declaration itself.

Optional — the power tool

A debugger can show you memory without writing any program at all. On your Mac it's lldb, and it needs enabling once. Run this yourself in your terminal — it will ask for your password, which is why I can't run it for you:

$ sudo DevToolsSecurity --enable

Then, having compiled with -g to keep the debugging information:

$ cc -g -O0 peek.c -o peek
$ lldb ./peek
(lldb) b main
(lldb) run
(lldb) next
(lldb) x/4xb &n      # examine 4 bytes, in hex, at the address of n
(lldb) p n           # print n through its own lens
(lldb) p/x n         # print n in hexadecimal

Do this after the exercises, not instead of them. Writing dump yourself teaches you what the debugger is doing; starting with the debugger teaches you which keys to press.

Before you move on. Everything here came from one sentence: a type is a lens, not a property of the bytes. Check that you own it rather than remember it — tomorrow, cold, explain to yourself why -1 < sizeof(int) is false, without using the word "unsigned" until you've first said what the bytes are doing. If you can't, reread the trap. That single example contains the whole rung.

Execution Context & the Call Stack

Let's start with something you already believe, so completely that you've probably never stated it out loud: nothing exists until its line has run.

In Python, if you write

print(x)
x = 7

you get a NameError. Obviously. x isn't a name yet — the assignment hasn't executed. The interpreter reads top to bottom, and a variable is born the instant its line fires. Before that line, as far as the interpreter is concerned, that name simply does not exist. You've built your whole intuition for how code runs on this one idea, and it has never once betrayed you.

Now here's the same shape of program, in JavaScript.

console.log(x);
var x = 7;
Before you open this — what does JavaScript do here? Same as Python?

It prints undefined.

Not an error. Not 7. A specific, deliberate value: undefined. Something was already sitting in x before line 1 ran — line 2 hadn't executed yet, so it couldn't be 7. But it also wasn't nothing, or we'd have gotten Python's error. It was something, holding the shape of x, empty.

Sit with that for a second, because it's genuinely strange. Whatever your mental model of "the interpreter reads top to bottom and things spring into existence when their line runs" was — it just failed. Something existed before its line ran.

Let's push on the crack. Same idea, with a function instead of a variable:

getName();

function getName() {
  console.log("Namaste JavaScript");
}
Predict this one too — calling a function before its definition even appears in the file.

It runs. Completely normally. Prints Namaste JavaScript, no error, no undefined — the entire function was usable before the parser had even "seen" it written on the page.

So now we have two data points, and they disagree with each other in an interesting way:

  • x existed early, but empty — undefined.
  • getName existed early, and fully functional — the whole thing.

A tempting cheap explanation: "maybe JS just does a quick first pass to find all the function definitions, then runs the file normally." That would explain getName working early. But it doesn't explain x. If JS only pre-scanned for functions, x should still throw ReferenceError, same as Python — x isn't a function, there'd be nothing for that pre-scan to find. Yet it didn't throw. It gave us a real, if empty, box.

So the pre-scan isn't only looking for functions. It's reserving a spot for every single variable and function in the program, before running a single line — and it fills each spot differently depending on what it is. That's the actual idea. Let's build it properly.

The execution context

Here's the core fundamental, and everything else in this series — hoisting, scope, closures, this, the event loop — is a consequence of this one fact:

Everything in JavaScript runs inside an execution context.

Picture it as a box. The box has exactly two compartments:

  • a memory component (also called the variable environment) — a set of key–value pairs, where variable and function names are the keys.
  • a code component (also called the thread of execution) — the place where lines actually get run, one at a time, in order.

The box is built in two separate phases, and this is the part your Python intuition is missing entirely:

Phase 1 — memory creation. Before executing anything, JS walks through every line belonging to that box — for the global context, that's the top-level code; for a function's context (more on this below), just what's inside that function — and for every var and every function declaration it finds, it reserves a slot in the memory component. It doesn't run any code in this pass — it just allocates.

What goes in each slot depends on what it is:

  • a var gets the placeholder value undefined.
  • a function declaration gets the entire function — the whole code, copied in, ready to run.

Phase 2 — code execution. Only now does JS go back to line 1 and actually run the program, top to bottom, replacing each undefined with its real value as the corresponding assignment line executes.

Rerun the two snippets above in your head with this model:

By the time console.log(x) fires, phase 1 has already reserved x and set it to undefined — so that's exactly what prints. 7 doesn't exist yet because line 2, the assignment, hasn't run.

By the time getName() fires, phase 1 has already copied the whole function body into the getName slot — nothing left to wait for, so it just runs.

This is why undefined is not an error and not "nothing" — it's a specific, deliberate placeholder JS writes into every reserved-but-not-yet-assigned var slot. Later you'll meet a case (a function expression — an arrow function assigned to a variable) where a "function" behaves like x instead of like getName, because to JS, it is a variable, not a declaration. Worth predicting for yourself before that lesson.

Functions get their own box

So far we've only watched the outermost box — the one JS builds for your whole program the moment it starts running, called the global execution context. But functions are where this gets interesting. Take this:

var n = 2;

function square(num) {
  var ans = num * num;
  return ans;
}

var square2 = square(n);
var square4 = square(4);

Global phase 1 reserves n, square, square2, square4 — n, square2, square4 get undefined; square gets the whole function copied in. Global phase 2 begins: n becomes 2. Then line 6 runs: square(n) — a function invocation.

Here's the rule: every time a function is invoked, a brand-new execution context is created just for that call — its own two-compartment box, its own memory phase, its own code phase, totally separate from the global one. Inside this box, phase 1 reserves memory only for what's local to that call — the parameter num and the variable ans — both undefined to start. Then its own phase 2 runs: num gets the argument 2, ans gets computed as 4, return hands 4 back to where square(n) was called from, and — this matters — the moment the function finishes, its entire execution context is thrown away. Gone. Then line 7 runs: square(4) creates a whole new, equally disposable box, computes 16, and vanishes the same way.

Notice what this buys you: if square had a local variable named n too, it would not collide with the global n — each execution context's memory is its own sealed room. Two different calls to the same function, even reusing a variable name, get two completely independent boxes that know nothing of each other.

Quick check: two functions, same local variable name — will they interfere? 
function a() {
  var x = 10;
  console.log(x);
}
function b() {
  var x = 100;
  console.log(x);
}
a();
b();

Prints 10 then 100. Each call gets its own sealed execution context with its own x — they never see each other, even though the name is identical.

The call stack

If every function call spins up a new box, and functions can call functions can call functions, JS needs a way to track "which box am I in right now, and where do I go back to when this one's done?" It manages this with a stack, literally called the call stack (also called the execution context stack, program stack, control stack, runtime stack — all the same thing, JS just loves extra names for one idea).

The rule is simple: whenever an execution context is created, it's pushed onto the stack. Whenever one finishes, it's popped off, and control returns to whatever's now exposed underneath.

Walking through square(n) then square(4) from before:

1. program starts 2. square(n) is called 3. square(n) returns, square(4) is called ┌───────────┐ ┌───────────┐ │ square(n) │ │ square(4) │ ┌───────────┐ ├───────────┤ ├───────────┤ │ GEC │ │ GEC │ │ GEC │ └───────────┘ └───────────┘ └───────────┘

The global execution context (GEC) always sits at the bottom — it's created the instant your program starts, and it's the last thing to be popped, once every line has run. square(n) is pushed on top when it's called, popped the moment it returns, then square(4) is pushed the same way. Everything stacks on top of the GEC in the order it was invoked, and unwinds in the reverse order it finishes — which is exactly why a function three calls deep still correctly returns control to the call that made it, and not to some other one.

The shortest JavaScript program

Here's a question worth actually sitting with: what does an empty file do?

// (nothing here at all)
Does an empty file create an execution context?

Yes. Even with zero lines to run, JS still creates a global execution context the moment the program starts — because "create the GEC" isn't something your code triggers, it's the very first thing that happens, unconditionally, before your code is even looked at.

And that GEC isn't actually empty either. Two things come bundled with it automatically, for free, in every JS environment:

  • a global object — in a browser, this is called window.
  • this — at the global level, this simply points at that global object. this === window, right from the start, before you've written a single line.

And here's the part that ties it back to everything above: any var or function you declare outside of any function — at the top level of your file — doesn't just sit in some abstract "global memory." It gets attached as a property of that same global object. Declare var x = 7 at the top level, and window.x is 7 too. They're the same slot.

Node.js (running JS outside a browser) uses a different name for the global object, but the shape of the idea is identical — every JS environment is responsible for handing you a global execution context with a global object and a this, before your code runs at all.

Your turn

Predict the output, in order, before opening the answer. Use nothing but: phase 1 reserves memory for every var and function in a context before phase 2 runs anything; every function call gets its own fresh, sealed context.

console.log(x);
console.log(sum(2, 3));

var x = 10;

function sum(a, b) {
  console.log(y);
  var y = a + b;
  return y;
}
Reveal

undefined, then undefined, then 5.

Global phase 1 reserves x (→ undefined) and sum (→ whole function). Phase 2 begins: line 1 prints x — still undefined, since line 4 (the assignment) hasn't run yet. Line 2 calls sum(2, 3), which spins up its own context: its own phase 1 reserves y as undefined before sum's phase 2 does anything; so console.log(y) inside sum prints undefined too — not 5, because var y = a + b hasn't executed yet. Then it does, y becomes 5, and return y hands 5 back out to the outer console.log, which prints it.

Where this leaves you

You now have the one fact everything else in this series hangs off: JS builds a box before it runs anything, fills the box's memory in one pass, then executes in a second pass — and every function call gets its own disposable box, tracked by a stack. Hoisting, next, is just this same fact restated as a phenomenon. Scope, closures, this in a function (not just globally) — all consequences of what a box remembers and what it forgets.

One honest note before you move on: you just read this, and reading feels like understanding. It isn't, yet. Open your browser console right now, paste in the sum example above, put debugger; as the first line, and step through it — watch the Scope panel actually fill with undefined before your eyes, watch the call stack panel grow and shrink as sum is entered and left. You own this once you've watched it happen without me telling you what you'd see, and can predict a snippet you've never seen with the same confidence you'd predict Python.

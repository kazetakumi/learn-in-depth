Scope & the Lexical Environment

You already own a fact that's about to seem like a problem: each function call gets its own sealed execution context. Sealed enough that in crux 1, two functions with a local variable of the same name never interfered with each other — separate rooms, separate memory, no leakage between siblings.

So here's the question worth sitting with before you write a single line: if every execution context is its own sealed room, how does this work?

function a() {
  var b = 10;

  function c() {
    console.log(b);
  }
  c();
}
a();
Predict it. c never received b as a parameter, never declared it. Sealed room, remember.

It prints 10. Completely fine, no error, no undefined. c reached straight into a's memory and read b as though it were local.

So "sealed" was too strong a word. There's clearly a door somewhere. Let's find out exactly where it opens — and, just as importantly, which direction it opens.

function a() {
  function c() {
    var b = 10;
    console.log(b);
  }
  c();
  console.log(b);
}
a();

Same three functions, but now b lives in the innermost one, and the second console.log tries to reach it from outside, one level up.

Does the door swing both ways?

c's own console.log(b) prints 10, no surprise. But a's console.log(b) — reaching from the outside in — throws Uncaught ReferenceError: b is not defined. Same error you met in crux 2, for the same underlying reason: no slot named b exists anywhere a is allowed to look.

Now you have both halves. An inner function can reach outward into everything containing it. An outer function can never reach inward into what a function it called declared locally. The door only opens one way — inward looking out.

This — where in your code a given variable can be legally touched — is exactly what scope means. Nothing more mystical than that. "What's the scope of b" and "is b in scope here" are the same question asked from two directions.

Lexical environment: the actual door

Here's the mechanism, and the word lexical is doing real work, so don't skim past it. Lexical means: where something physically sits, written in the source code — not who called it, not when, just where it's sitting on the page. In the very first example, c is written physically inside a. That single fact — nothing about how or when c gets called — is what makes a "the lexical parent" of c.

This is worth pausing on, because it didn't have to be this way. Imagine a different rule: a function's scope is decided by whoever calls it, not by where it's written — that's a real design called dynamic scoping, and a few older languages actually work that way. JavaScript doesn't. It fixes scope permanently, once, based purely on the physical nesting in the source — which is exactly why you can read a JS file top to bottom and know precisely what every line can see, without ever having to trace who might call what at runtime.

Now the actual rule: every time an execution context is created, it also gets a lexical environment — and a lexical environment is nothing but two things bolted together: that context's own local memory, plus a reference to the lexical environment of whatever function physically contains it. Not a copy — a live reference, a pointer, to the parent's own lexical environment, which itself holds a reference to its parent, and so on, all the way up.

Walk it for the three-deep version — global, containing a, containing c:

lexical env of c lexical env of a lexical env of global ┌──────────────────────┐ ┌──────────────────────┐ ┌──────────────────────┐ │local memory of c │ │local memory of a │ │local memory of global│ │ (nothing local) │ │ b: 10 │ │ a: function │ │ │ │ c: function │ │ │ │parent ref │──►│parent ref │──►│parent ref: null │ └──────────────────────┘ └──────────────────────┘ └──────────────────────┘

When console.log(b) runs inside c: JS looks in c's own local memory first. Not there. So it follows the parent reference — straight to a's lexical environment — and looks there. Found: 10. Done.

If it hadn't been found in a either, the exact same move repeats: follow that parent reference, land in global's lexical environment, search again. Global's own parent reference points to null — there's nowhere left to go. If the search reaches null still empty-handed, that's the moment JS gives up and throws ReferenceError: b is not defined.

This whole walk — local memory, then parent, then parent's parent, then parent's parent's parent, until either the variable turns up or you hit null — has a name: the scope chain. That's genuinely the whole definition. Not a separate structure JS builds specially — just the trail of "follow the parent reference" left behind by however deeply your functions happen to be nested in the source.

One thing worth noticing now and setting aside for later: c keeps working even though it's reaching into a's memory from inside a nested call. What happens if c gets called after a has already finished and its execution context is supposedly gone? That question is crux 5 — closures — and the honest answer will surprise you a little.

Your turn

Three levels deep this time, each with its own local variable, plus one access that breaks the one-way rule. Predict every line.

function outer() {
  var x = "outer x";

  function middle() {
    var y = "middle y";

    function inner() {
      var z = "inner z";
      console.log(x, y, z);
    }

    inner();
    console.log(z);
  }

  middle();
}

outer();
Reveal

inner's console.log(x, y, z) prints outer x middle y inner z. All three are reachable, because inner's scope chain runs inner → middle → outer → global, and each of x, y, z turns up at exactly the link where it was declared. Notice inner never had to be handed x or y as parameters — the chain found them on its own, purely from where inner sits in the source.

middle's console.log(z) throws Uncaught ReferenceError: z is not defined. z only exists in inner's local memory, and middle's scope chain — middle → outer → global — never runs through inner at all. The door only opens looking outward; middle has no way to look back down into a function it merely called.

Where this leaves you

Scope isn't a rule you memorize function by function — it's the direct, mechanical consequence of one fact: every execution context carries a live reference to its lexical parent's environment, fixed permanently by where the code is physically written. "Can I reach this variable" is just "does the scope chain, walked from here, hit it before hitting null." Hold onto that image of the chain — closures, two lessons from now, is what happens when a link in that chain refuses to disappear even after the function that created it has returned.

Don't stop at having read the diagram. Paste the outer/middle/inner example into your console, put debugger; as the first line inside inner, and open the Scope panel when it pauses there. You'll see it labeled exactly the way you'd hope by now — Local, then Closure (middle), then Closure (outer), then Global — the scope chain, rendered as literal nested entries, not something I'm asking you to take on faith.

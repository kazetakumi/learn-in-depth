let, const, the Temporal Dead Zone & Block Scope

Here's a fact that should immediately bother you, given what you know: let and const are hoisted too. Phase 1 reserves them in memory before any code runs, exactly like var. So — same setup as crux 2 — what happens here?

console.log(a);
let a = 10;
You already have a rule for this shape of program. Apply it.

Not undefined. Uncaught ReferenceError: Cannot access 'a' before initialization.

Read that message closely — it's not the same error as an undeclared variable either. Crux 3 taught you ReferenceError: a is not defined, for a name that was never in the scope chain at all. This message is different on purpose: "Cannot access... before initialization." JavaScript is telling you a exists. It's reserved. You're just not allowed to touch it yet.

So now there are three distinct behaviors for "touch a name before its assignment line runs," and you've just met the third:

var ahoisted, given undefined immediately — freely readable, just empty.
never declarednever reserved anywhere in the scope chain — ReferenceError: not defined.
let / const ahoisted, reserved — but locked. ReferenceError: Cannot access before initialization.

The temporal dead zone

Notice the word JS chose: temporal. Crux 3 was built entirely on lexical — where something sits, physically, in the written code, fixed forever the moment you write it. This is different. Temporal means about time — specifically, time during execution, phase 2, as your program actually runs line by line.

let and const get reserved in phase 1 same as anything else, but into a separate, guarded pocket of memory — not the ordinary slot var uses. From the moment their scope starts executing until the exact line where they're declared actually runs, they sit in that guarded pocket, completely untouchable. That entire stretch of time has a name: the temporal dead zone (TDZ) — dead, because nothing you do to the variable in that window works; temporal, because the boundary is a moment in execution time, not a location in the code.

The scope chain from crux 3 tells you where you're allowed to look for a variable. The TDZ tells you when, even once you've found the right box, you're allowed to actually open it.

This isn't JS being needlessly strict. Think about what the alternative would cost you: with var, accidentally reading a variable before you meant to assign it silently gives you undefined — a bug that runs quietly and shows up as wrong output three functions later. The TDZ turns that same mistake into a loud, immediate, impossible-to-ignore crash, right at the line that's actually wrong.

const adds two more rules

const does everything let does — hoisted, TDZ, all of it — plus two extra constraints that fall directly out of what the word means: a constant.

const b;
Predict this one — declaring a const with nothing assigned.

Uncaught SyntaxError: Missing initializer in const declaration. Not even a runtime error — the program refuses to parse at all. Since a const can never be assigned later, JS can't let you declare one without a value; there'd be no legal line left where it could ever receive one.

const c = 10;
c = 20;
And reassigning one after the fact?

Uncaught TypeError: Assignment to constant variable. This one waits until phase 2 actually reaches the offending line, which is why it's a TypeError and not a SyntaxError — the program is perfectly well-formed, it's just doing something forbidden at runtime.

One more, shared by both let and const, that var never enforced: you cannot declare the same name twice in the same scope.

let d = 1;
let d = 2; // Uncaught SyntaxError: Identifier 'd' has already been declared

var would have silently allowed this and just quietly overwritten the first d — a real source of bugs in large, old JS files. let/const close that door outright.

A distinction worth having ready for an interview: const locks the binding, not what it points at. const arr = [1]; arr.push(2); works completely fine — you've mutated the array, not reassigned arr to a different array. What throws is only arr = [1, 2], a genuine reassignment of the name itself.

Block scope

Everything so far has been about when. Now, one more piece of where — a scope chain link crux 3 never showed you, because var can't create one.

A block is just { } — the curly braces you already write around if, for, while. JS calls it a compound statement: a way of grouping several statements into one, for the places — like the body of an if — where the language only expects a single statement.

{
  var a = 10;
  let b = 20;
  const c = 30;
}

console.log(a); // ?
console.log(b); // ?
console.log(c); // ?
Same block, three different declaration keywords. Which survive outside it?

Only a — it prints 10. console.log(b) and console.log(c) both throw ReferenceError: not defined.

Here's why: a block, just like a function, gets its own lexical environment the instant execution enters it — its own local memory, its own link back to the parent's lexical environment, exactly the chain you already built in crux 3. let and const respect that boundary completely: declare one inside a block, and it lives only in that block's memory. Step outside the closing }, and the scope chain from out there simply doesn't run through it anymore — same as middle never being able to see into inner.

var never got the memo. It doesn't recognize block boundaries at all — it always attaches itself to the nearest enclosing function scope, or the global scope if there is no function. A block is invisible to it. That's why a survived and the others didn't: it was never really "in" the block to begin with.

Shadowing

Since a block gets its own slice of memory, you can reuse a name from an outer scope inside it — and the inner one temporarily hides, or shadows, the outer one for as long as you're inside that block.

let x = "outer";

{
  let x = "inner";
  console.log(x); // ?
}

console.log(x); // ?
Predict both logs.

"inner", then "outer". Inside the block, the scope chain finds the block's own x first and stops there — never even looks further out. Once the block ends, that inner x and its whole memory are gone, and the outer x was never touched.

This is completely safe with let/let or const/const, because each block genuinely gets its own separate memory. But remember var doesn't believe in block memory at all — so watch what happens when you try to shadow a let with a var:

function f() {
  let y = 20;

  {
    var y = 20;
  }
}
Is this "shadowing" too, the same way?

Uncaught SyntaxError: Identifier 'y' has already been declared. Fails before the program even runs.

This is illegal shadowing, and it falls straight out of two facts you already have in hand: var ignores the block and hoists y up to f's function scope — but there's already a let y sitting in that exact same function scope. Same collision as declaring let y twice in a row. The reverse direction is perfectly legal, and now you can predict why without being told:

var z = 20;

{
  let z = 30; // perfectly legal
  console.log(z); // 30
}
console.log(z); // 20
Here, let z stays confined to the block's own memory — it never tries to attach anywhere it isn't wanted, so there's nothing for it to collide with. Only var reaching outside its block causes trouble; let reaching outside its block is impossible by construction.

Your turn

TDZ and block shadowing, in one pass. Predict every line.

let score = 100;

function printScore() {
  console.log(score);
  let score = 200;
}

printScore();
Reveal

Uncaught ReferenceError: Cannot access 'score' before initialization.

The tempting wrong answer is 100 — "the inner score isn't declared yet, so surely the lookup falls through to the outer one." But it doesn't work that way. printScore's own execution context has a let score written inside it, so phase 1 of that context already reserved a local score — in the TDZ, locked — before console.log(score) ever runs. The scope chain finds that reserved-but-locked local slot first and stops right there; it never even continues outward to check the global score. Having a local declaration anywhere in a scope — even below where you read it — is enough to shadow the outer one for the entire scope, TDZ included.

Where this leaves you

let and const didn't get a new hoisting rule bolted on as an exception — they get the exact same phase-1 reservation as everything else, just written into a locked pocket of memory instead of an open one, for a span of execution time with a name: the temporal dead zone. Block scope is the same scope-chain machinery from crux 3, just with one more kind of node — a { } — allowed to open a link, something var was never taught to respect. Both traps you tested here — TDZ and illegal shadowing — are really the same lesson from two different angles: JS would always rather throw loudly at the exact wrong line than let a silent, wrong undefined slip three lines further down and become someone's 2am bug.

Go verify the block claim yourself, don't just take the prose for it: paste the shadowing example into your console, put debugger; inside the inner block, and look at the Scope panel when it pauses. You'll see a Block entry sitting right there alongside Local and Global — its own real link in the chain, not a syntactic illusion.

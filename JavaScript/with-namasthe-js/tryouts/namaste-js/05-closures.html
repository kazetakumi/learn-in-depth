Closures

Crux 1 gave you a rule you've trusted for four lessons now, and I planted a loose thread in crux 3 that it's time to pull: once a function returns, its execution context is deleted. Gone. Not archived, not paused — deleted. So predict this one using only what you already know:

function outer() {
  var counter = 0;

  function increment() {
    counter++;
    console.log(counter);
  }

  return increment;
}

var inc = outer();
inc();
inc();
outer() already returned before either inc() call. Its execution context — and counter along with it — should be gone. What happens?

It prints 1, then 2.

Not an error. Not undefined. A real number, that keeps incrementing, correctly, across two entirely separate calls made long after outer finished running. Something is holding counter alive that, by crux 1's rule, should not exist anymore.

The rule needed one more clause

"Deleted when the function returns" was never wrong — it was incomplete. The real rule: an execution context's memory gets reclaimed once nothing can reach it anymore. Usually, the moment a function returns, that's instantly true — nothing outside ever had a way to touch its local memory in the first place, so it's safe to throw away.

But increment is different. Remember crux 3: every execution context is created holding a live reference to its lexical environment — not a copy, a pointer. increment was written physically inside outer, so its lexical environment reference points straight at outer's local memory. When you return increment, you're not just handing back a function — you're handing back that function together with its live reference to outer's memory. As long as inc exists somewhere holding onto that returned function, outer's memory is still reachable through it. Not reachable — not deleted.

This bundle — a function, plus the lexical environment it was born into, kept alive together — is what a closure actually is. Not a special syntax, not something you opt into. Every single function in JavaScript forms one automatically, the moment it's created. You've been building closures since crux 3 without a name for it; most of them just never outlived the call that made them, so you never noticed the memory surviving.

This is also the honest answer to a question you might have quietly been sitting with: garbage collection. JavaScript reclaims memory once it's unreachable — and a closure is precisely what makes memory stay reachable past the point crux 1 would otherwise have deleted it. outer's execution context survives for exactly as long as something, somewhere, still holds a reference to increment. Set inc = null, and once nothing else references it, counter's memory finally becomes eligible for collection.

Reference, not value — the trap that catches everyone

Here's the detail that separates "I can define closure" from "I can predict what closures actually do," and it's the single most common closures interview question there is. A closure remembers a reference to a variable, not a snapshot of its value at creation time. Watch what that means:

function printNums() {
  for (var i = 1; i <= 5; i++) {
    setTimeout(function () {
      console.log(i);
    }, i * 1000);
  }
}
printNums();
Prints 1, 2, 3, 4, 5 — one per second? Predict before opening.

It prints 6, five times, at roughly one-second intervals.

Not what most people expect on the first pass, and it's worth sitting with why.

Walk it through with what you actually know, not what feels intuitive. The five callbacks passed to setTimeout each form a closure — but a closure over what? var is function-scoped, not block-scoped (crux 4). There is exactly one i for the entire loop, one single memory slot, and all five callbacks close over that same slot — five separate functions, one shared reference.

Second piece: JavaScript does not pause the loop to wait for a timer. setTimeout hands its callback off, attaches a timer, and JS immediately moves to the next iteration — it'll be crux 7 before you see exactly how, but for now just trust that the loop runs to completion essentially instantly, all five callbacks scheduled, long before even the first timer (1000ms) has expired. By the time any of them actually fires, i has already been incremented all the way past the loop's exit condition, landing at 6. All five closures share that one slot — so all five print whatever's sitting in it now: 6.

Notice the delays themselves — 1000ms, 2000ms, 3000ms, 4000ms, 5000ms — still come out staggered and correct, even though every logged value is 6. That's not a contradiction, it's the whole lesson compressed into one line: i * 1000 is computed immediately, on each pass through the loop, and handed to setTimeout as a plain number — done, fixed, no reference involved. What runs inside the callback, console.log(i), is a closure over the variable itself, read fresh at fire time, long after the loop and every value it ever held except the last are gone. Same i, two completely different relationships to it.

You already know the one-line fix, and you can predict why it works before I say it:

function printNums() {
  for (let i = 1; i <= 5; i++) {
    setTimeout(function () {
      console.log(i);
    }, i * 1000);
  }
}
printNums();
Same code, var swapped for let. Why does this print 1 through 5?

Because let is block-scoped, and — a fact from crux 4 worth having ready — the spec makes a for (let ...) loop create a genuinely fresh binding of i for every iteration, not one shared slot. Five iterations, five separate memory locations, each holding its own value. Each callback's closure now points at its own private i, untouched by the other four — so each prints exactly the value it captured.

Worth knowing for an interview that specifically forbids let: you can fix the var version by hand, using nothing but what you already understand about closures — wrap the scheduling in its own function, called fresh each iteration:

function printNums() {
  for (var i = 1; i <= 5; i++) {
    function scheduleLog(i) {
      setTimeout(function () {
        console.log(i);
      }, i * 1000);
    }
    scheduleLog(i);
  }
}
printNums();

Each call to scheduleLog spins up its own execution context (crux 1) with its own parameter i, a fresh copy each time — and the inner function closes over that private copy instead of the loop's shared one. Same fix as let, hand-built out of function scope instead of block scope.

The other thing closures are good for: hiding data

A global variable is public property — anything, anywhere in your program, can reach in and change it. If you need a counter that only your own code is allowed to touch, closures give you that for free, no special syntax required:

function makeCounter() {
  let count = 0;

  return function () {
    count++;
    return count;
  };
}

const counterA = makeCounter();
counterA();

console.log(count); // ?
Predict the final line.

Uncaught ReferenceError: count is not defined. count was never in the global scope chain to begin with — it lives only in makeCounter's local memory, kept alive by the closure the returned function carries. The only way to touch it, ever, is through counterA(). No other code, anywhere, has a path in.

Your turn

Two independent calls to the same factory. Predict all four lines.

function makeCounter() {
  let count = 0;
  return function () {
    count++;
    return count;
  };
}

const counterA = makeCounter();
const counterB = makeCounter();

console.log(counterA());
console.log(counterA());
console.log(counterB());
console.log(counterA());
Reveal

1, 2, 1, 3.

Every call to makeCounter() creates a brand-new execution context, with its own brand-new count — crux 1's rule, completely unaffected by any of this. counterA and counterB are two entirely separate closures, each holding a reference to its own private count, never each other's. counterA climbs 1, 2, pauses while counterB starts fresh at 1, then counterA resumes exactly where it left off, at 3 — because its particular closure's memory was never touched by anything counterB did.

Where this leaves you

A closure was never a feature you turn on — it's what a function is, once you take crux 1's execution context and crux 3's live lexical-environment reference seriously at the same time. Every function carries its birth environment with it, permanently, wherever it goes; that's why it can keep working with variables from a scope that's technically already "returned." The loop-and-setTimeout trap and the private-counter trick are the same fact, aimed in two different directions: one is what happens when several closures accidentally share one slot, the other is what happens when you deliberately make sure nothing else can reach a slot at all.

Put debugger; inside increment from the very first example, run it, and open the Scope panel. You'll see an entry labeled, literally, Closure (outer), with counter sitting inside it — memory that crux 1 said should already be gone, named and made visible by your own devtools, not by me telling you to trust it.

Hoisting

Last time you built the actual mechanism: JS creates every execution context in two passes — a memory-creation phase that reserves a slot for every var and function in that context, then a code-execution phase that runs your lines and fills those slots in for real. You don't need that story re-told. What you need now is its name, and the two traps hiding inside it that catch almost everyone — including, very often, the interviewer's favorite question.

The name first, because you'll want it: this whole phenomenon — being able to touch a variable or function before its line has run — is called hoisting. Not because JS physically moves your code to the top of the file, which is the explanation you'll hear most often and the one you should never give in an interview. Nothing moves. The memory was simply reserved before any line ran, full stop — hoisting is just the name for the visible effect of that.

Trap 1 — undefined is not the same as absent

You already know console.log(x) before var x = 7 prints undefined, because phase 1 reserved a slot for x. Now the sharper question:

console.log(y);

— where y was never declared anywhere in the file. Not above, not below. It simply doesn't exist in your program at all.

Same result — undefined? Or something else?

Uncaught ReferenceError: y is not defined. A hard error, not a graceful placeholder.

This is the distinction almost everyone blurs, and it falls straight out of what you already know about phase 1. Phase 1 only reserves a slot for names it actually finds while scanning the context — a var statement, a function declaration. y was never declared, so phase 1 never touched it — there's no slot to look up, so JS has nothing to hand back but an error.

undefined is also not "empty" or "nothing" the way you might assume — it's a genuine value, occupying a genuine slot, that you can test for directly:

if (a === undefined) {
  console.log("a is undefined");
}

It behaves like this because JS is loosely typed — a variable's slot isn't committed to holding any particular kind of value. The same slot can hold undefined, then a number, then a string, one after another, with no complaint. undefined is simply whichever value happens to be sitting there before you've assigned anything else.

You can write a = undefined yourself — JS won't stop you. But don't. undefined means "JavaScript put this here because nothing else has been assigned yet." If you assign it by hand, you've destroyed that signal — now you can't tell whether a slot is genuinely untouched or whether someone deliberately blanked it. Let JS own that value; you own everything else.

Trap 2 — not all functions hoist the same way

Back in crux 1 you saw this work with no error at all:

getName();

function getName() {
  console.log("Namaste JavaScript");
}

Now change exactly one thing — write the same function as an expression instead:

getName();

var getName = function () {
  console.log("Namaste JavaScript");
};
Predict it. It's still "the same function," right?

Uncaught TypeError: getName is not a function.

Not a ReferenceError — JS clearly found something named getName. It just wasn't a function yet.

Here's why, and it's a direct replay of the rule you already own: phase 1 doesn't look at what's on the right side of = to decide how to treat a name — it looks at how the name was introduced.

  • function getName() {...} is a function declaration. Phase 1 recognizes the whole shape and copies the entire function body into the slot immediately.
  • var getName = function () {...} is a variable, full stop, that happens to be assigned a function value on the right. To phase 1, this is indistinguishable from var getName = 7. It reserves getName and fills it with undefined — same as any other var. The function body only gets attached when phase 2 actually runs that assignment line.

So getName() on line 1, before phase 2 has reached the assignment, is really trying to call undefined() — and calling something that isn't a function is exactly what TypeError means. Arrow functions assigned to a variable hoist identically, for the same reason — var getName = () => {...} is still just a variable assignment to phase 1:

getName(); // TypeError: getName is not a function

var getName = () => {
  console.log("Namaste JavaScript");
};
File this one away rather than resolving it now: let getName = function() {...} hoists the identifier too — but touching it before its line runs doesn't give you undefined at all. It throws a different error, immediately, for a reason that needs its own lesson — it's called the temporal dead zone, and it's crux 4.

Your turn

One snippet, both traps. Predict every line, top to bottom, before opening the reveal — and predict what actually gets printed to the console, not just what each line "would do" in isolation.

console.log(a);
console.log(sayHi);
console.log(sayBye);
sayBye();

var a = 5;

function sayHi() {
  console.log("hi");
}

var sayBye = function () {
  console.log("bye");
};

console.log(b);
Reveal

console.log(a) → undefined — a is a var; phase 1 reserved it, phase 2 hasn't reached var a = 5 yet.

console.log(sayHi) → the whole function, printed directly. It's a declaration, so phase 1 copied its entire body in — nothing left to wait for.

console.log(sayBye) → undefined. sayBye is a var that happens to be assigned a function expression; phase 1 treats it exactly like var sayBye = 7 and reserves only the identifier.

sayBye() → Uncaught TypeError: sayBye is not a function. That slot still holds undefined at this point in the program — you're calling undefined(). This is trap 2, firing exactly where you can watch it.

And that's it. The TypeError is uncaught, so the script halts right there — console.log(b) on the last line never runs, and it doesn't matter that b was never declared either. You don't even get to find out it would have been a ReferenceError. Once one uncaught error fires anywhere in a script, everything after it — regardless of what it was going to do — is simply never reached. That's worth remembering for its own sake: an interviewer stacking multiple "gotcha" lines after a line that throws is often testing whether you know the later lines are already irrelevant.

Where this leaves you

Hoisting was never a rule to memorize — it's what the two-phase execution context looks like from the outside, for two different kinds of things: variables get a slot and a placeholder, function declarations get a slot and their whole body, and anything written as an assignment (var x = function(){}, var x = () => {}) is a variable first and a function second, with all of a variable's hoisting quirks attached. Next time an interviewer asks "what is hoisting," you now have the real answer instead of the folk one — and you can predict the TypeError trap before you've even run the code.

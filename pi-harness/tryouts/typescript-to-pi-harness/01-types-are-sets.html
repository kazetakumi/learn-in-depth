A type is a set of values

One sentence. Everything else in this language is a consequence of it.

Rung 0 was all JavaScript — not a single type appeared. Today we add them, and I'm going to make a claim that sounds far too simple to be worth a lesson:

Every type in TypeScript is a set of values.
extends means ⊆.

That's the whole rung. If you take those two lines seriously — and I mean compute with them, not nod at them — then never, unknown, structural typing, why intersections give you more properties, and half the error messages that will otherwise baffle you all stop being facts to memorise. They become things you can work out at the desk.

But I don't want to hand you that. Let's break your Python instinct first, because it's about to be wrong in a specific and interesting way.

What you currently believe a type is

In Python, a type is a class. It's a thing an object is. And membership is declared — an object is a Dog because it was built by Dog, and you can ask it at runtime: 

# Python. Membership is a fact about the object's ancestry.
class Dog:
    def __init__(self, name): self.name = name

d = Dog("rex")
isinstance(d, Dog)   # True — and Python can answer this
type(d).__name__     # 'Dog'

Now here's TypeScript. Read it and tell me what happens.

interface Dog {
  name: string;
}

const thing = { name: "rex", legs: 4 };

const d: Dog = thing;   // ← ?

Before you scroll. Does that last line compile?

thing was never declared to be a Dog. It doesn't inherit from anything. It has an extra property nobody asked for. Your Python head says this is obviously an error. Commit to an answer.

It compiles. No error, no warning, no cast.

I ran it — TypeScript 5.9.3 with every strict flag on. Clean.

So whatever a Dog is, it is not "a thing built by the Dog constructor." thing never heard of Dog. The two were written by people who never met. And it's still a Dog.

You've seen this idea before, though — you just saw it as the exotic option rather than the default. This is typing.Protocol. It's duck typing, promoted from a runtime accident to a compile-time rule. If it has the shape, it qualifies.

Good. So membership isn't declared, it's earned by shape. That's called structural typing, and it's the default here, not an opt-in.

Which suggests a better theory: a type is a shape — a set of required properties.

That theory is also wrong. Here's what kills it:

type Color = "red" | "blue";

const c: Color = "red";     // fine
const d: Color = "green";   // Type '"green"' is not assignable to type 'Color'

What shape does "red" have?

It's a string. It has no properties you care about. And yet "red" is a type here — a type with, apparently, exactly one thing in it. If a type were a shape, this line couldn't exist. So what is it?

The reframe

Stop asking what a type is. Ask what values it contains.

TypeThe set of values it contains
stringevery string. Infinitely many.
"red"exactly one value: the string "red".
"red" | "blue"two values. The | is set union.
booleantwo values: true and false.
{ name: string }every value that has a string name. Infinitely many, and most of them have other stuff too.
unknownevery value there is.
neverno values at all. The empty set.

Every row works. The theory survives literal types, object types, unions, and the two weird ones at the bottom that nobody ever explains properly.

And notice boolean. If types are sets, then boolean isn't a primitive at all — it's just true | false, a two-element set. That sounds like a cute reframing. It isn't; it's literally true, and you can make TypeScript admit it: 

type OnlyTrue = Exclude<boolean, false>;

const t1: OnlyTrue = true;    // fine
const t2: OnlyTrue = false;   // Type 'false' is not assignable to type 'true'

You just did set subtraction on a primitive type and got a smaller set back. That isn't a metaphor for what the compiler does. It's what the compiler does.

The rule that does all the work

Now the payoff. What is the type checker actually doing when it checks const x: B = a?

It's asking one question: is every value that could be in A also in B? Is A ⊆ B? If yes, the assignment is safe — whatever a turns out to hold at runtime, it's a legal B. If no, there's at least one value that would break the promise, so it errors.

Assignability is subset. A is assignable to B exactly when A ⊆ B.

Which brings us to the question most people get backwards. Take your time on this one.

type Person = { name: string };
type Employee = { name: string; salary: number };

Which is the subset? Answer before opening.

Is Employee ⊆ Person, or Person ⊆ Employee? Employee has more properties — so is it the bigger set or the smaller one?

Then: which direction of assignment compiles?

Employee is the SMALLER set

Count values, not properties. Person is every value with a string name. That includes {name:"a"}, {name:"a", salary:5}, {name:"a", legs:4}, a dog, a spaceship — anything at all, so long as it has a name.

Employee demands a name and a salary. Every value that qualifies as an Employee also qualifies as a Person. But not the reverse. So Employee ⊆ Person.

Each property you add is another filter. More requirements, fewer survivors.

And so, by the subset rule, assignment runs the way sets say it must:

declare const e: Employee;
const p: Person = e;      // fine — Employee ⊆ Person

declare const p2: Person;
const e2: Employee = p2;  // error — Person ⊄ Employee (no salary)

Verified, both lines. And notice you now have a one-word answer for a question that trips people up forever: why can I pass a bigger object where a smaller one is wanted? Because the bigger object is the smaller set.

Hold onto that inversion, because it makes the next one predictable instead of insane.

Two quick ones. Answer both, then open.

1. { name: string } & { age: number } — the intersection. Does the resulting type have more properties, or fewer?

2. "red" | "blue" versus "red" — which is assignable to which?

Both fall out of set arithmetic

1. More properties. The intersection is the values that are in both sets — things that have a name AND an age. That's a smaller set, and smaller sets of object values are described by longer property lists.

So &, which reads like "and", produces a type with more fields, while |, which reads like "or", produces a type with fewer usable fields. That looks backwards right up until you stop thinking about properties and start counting values. Then it's forced. 

type Both = { name: string } & { age: number };
const b1: Both = { name: "x", age: 1 };   // fine
const b2: Both = { name: "x" };           // error — missing age

2. "red" is assignable to "red" | "blue", not the other way. One element is a subset of two. A union is wider — less specific, less useful, safer to receive and harder to satisfy.

Now derive the two strange ones yourself

never and unknown get taught as trivia. They aren't. They're the two boundary cases of a set lattice, and if you hold the sets idea you can derive every one of their behaviours without being told.

Reason these out. All four.

never is the empty set ∅. unknown is the universal set 𝕌.

1. Can you assign a never to a string?

2. Can you assign anything at all to an unknown?

3. Can you assign an unknown to a string?

4. What type is string & number?

All four, straight from ⊆

1. Yes. ∅ ⊆ string — vacuously, since there's no counterexample to find. So never is assignable to every type. It feels like a special case in the compiler; it's just the empty set behaving normally.

2. Yes. Every set ⊆ 𝕌. So anything can be assigned to unknown.

3. No. 𝕌 ⊄ string. Which is exactly why unknown is the safe version of any: it accepts anything, then refuses to let you do anything with it until you've proved what it is. That proof is narrowing — rung 2, and it's the whole lesson.

4. never. No value is simultaneously a string and a number, so the intersection is empty, and the empty set is never. TypeScript will print never at you. That's not an error message; it's an answer.

All four verified.

Look at what just happened. You didn't learn four facts about never and unknown. You applied one rule four times. That's the difference the sets idea buys, and it's the reason this rung exists.

The one that isn't a set

Which leaves any. Try to place it in the lattice:

declare const a: any;
const s: string = a;   // fine
const n: number = a;   // fine
const back: any = "x"; // also fine

any is assignable to everything and everything is assignable to it. For a real set that's impossible — it would have to be both ∅ and 𝕌 at once. So any isn't a set at all. It's a hole in the floor. It means stop checking.

And that's why pi's own AGENTS.md says, flatly: "No any unless absolutely necessary." Not style policing. Every any is a place where the algebra stops running and the compiler quietly agrees to guess. unknown is what you almost always wanted: same openness at the door, no surrender of the guarantee.

The exception you'd otherwise think was a bug. I told you Employee ⊆ Person means you can assign one to the other. True — but watch: 

const ok: Person = employeeValue;                  // fine
const no: Person = { name: "x", salary: 5 };      // error!

Same set relationship, different answer. Because the second is a fresh object literal, written right there at the assignment, and those get an extra check called excess property checking. Set-wise it's perfectly legal; TypeScript rejects it anyway.

It's a deliberate exception, and a good one — a literal with a property the target doesn't want is almost always a typo or a misremembered field name, not a clever use of subtyping. But it is a lint rule bolted on top of the algebra, and it's the one place where "types are sets" will seem to lie to you. Assign through a variable and the exception disappears. I checked both.

The part that will actually bite you

Everything so far said the sets are real. Here's the twist, and it's the one thing on this page your Python background will fight hardest.

Compile this file:

interface Dog { name: string }
type Color = "red" | "blue";

const d: Dog = { name: "rex" };
const c: Color = "red";

Here is the complete JavaScript that comes out the other side:

const d = { name: "rex" };
const c = "red";
The types are gone. Not minified — gone. interface Dog compiles to zero bytes.

This is erasure, and it is the deepest difference between TypeScript's types and yours. In Python your annotations survive into the running program. You can read them with typing.get_type_hints(). That's not a curiosity — it's the entire mechanism Pydantic runs on: it reads your class at runtime, sees name: str, and builds a validator out of it.

None of that is possible here. There is nothing left to read.

So think about what that costs you, concretely.

Your agent receives a JSON blob over the network — a tool call from the model. You have an interface ToolCall describing its shape. Can you check the blob against that interface at runtime?

And if not, what do you have to do instead?

No. And this is why pi is built the way it is.

You cannot. interface ToolCall doesn't exist at runtime, so there's nothing to validate against. Types check the code you wrote; they say nothing about bytes arriving from outside. That data enters as unknown and stays dangerous until you narrow it.

So you need two artifacts:

1. a runtime value that describes the shape, so you can actually validate — a JSON schema;
2. a compile-time type of the same shape, so your editor helps you.

Write both by hand and they drift apart within a week — someone edits the schema, the type still claims the old shape, and the compiler cheerfully agrees with the lie. The fix is to write one and derive the other. That's exactly what pi does. From packages/agent/src/types.ts, the very first import: 

import type { Static, TSchema } from "typebox";

You define a schema — a real object, present at runtime, usable for validation — and Static<typeof schema> computes the TypeScript type from it. One source of truth, both worlds, no drift.

That is your Pydantic instinct, inverted to survive erasure. And Static is rung 4, where you'll write your own.

Read the real thing

Three lines from pi. You have everything you need for all of them.

// packages/ai/src/types.ts:82
export type ThinkingLevel = "minimal" | "low" | "medium" | "high" | "xhigh" | "max";

// packages/ai/src/types.ts:83
export type ModelThinkingLevel = "off" | ThinkingLevel;

// packages/ai/src/types.ts:393
export type StopReason =
  "pending" | "stop" | "length" | "toolUse" | "error" | "aborted" | "deferred";

ThinkingLevel is a six-element set. ModelThinkingLevel is that set plus one more element — a union used as literal set addition, in production, to say "a model may also be configured off, but you can't ask for off as an effort level." Two types, one relationship, no duplication.

Now the good one. This is the streaming event union, trimmed to its last two members:

// packages/ai/src/types.ts:534-539
| { type: "done";
    reason: Extract<StopReason, "stop" | "length" | "toolUse" | "deferred">;
    message: AssistantMessage }
| { type: "error";
    reason: Extract<StopReason, "aborted" | "error">;
    error: AssistantMessage }

Work it out. Extract<A, B> is set intersection.

StopReason has seven members. The done event takes some, the error event takes others. Count them. Which member is left over, and why did they leave it out?

They partitioned the set, and the leftover is the point

done takes four: stop, length, toolUse, deferred. error takes two: aborted, error. Four plus two is six, out of seven.

The leftover is "pending". And it's excluded on purpose: pending means still streaming. A terminal event, by definition, cannot be pending. So the type makes that unrepresentable — you could not construct a done event with reason: "pending" if you tried.

Sit with what that means. There's a category of bug — a finished event claiming to be unfinished — that cannot occur in this codebase. Not "is tested for." Cannot occur. That was bought with set intersection, in two lines, and it costs nothing at runtime because by then it's all been erased.

That is what the sets idea is for. Not passing a quiz on never — making illegal states unbuildable.

Your turn

Go to typescriptlang.org/play. Nothing to install, errors show up as you type. We'll set up a local toolchain at rung 6, when there's something to build.

Here's the technique I used to check every claim on this page, and it's worth stealing. // @ts-expect-error on the line before an error means "I predict this fails." If it doesn't fail, the compiler errors at you. So it turns a prediction into a test — you can assert that something is illegal, which is normally hard.

Paste this in and replace each ___ with your prediction:

type A = { id: string };
type B = { id: string; tag: "x" };

// 1. one of these is legal, one is not. Which way round?
declare const a: A; declare const b: B;
const t1: A = b;
const t2: B = a;

// 2. what type is this? hover it.
type Q = A & B;

// 3. and this one?
type R = ("x" | "y") & ("y" | "z");

// 4. predict, then check by hovering
type S = Exclude<StopLike, "pending">;
type StopLike = "pending" | "stop" | "error";

// 5. why does the SECOND line fail and the first not?
declare const wide: { id: string; extra: number };
const u1: A = wide;
const u2: A = { id: "x", extra: 1 };

Then the one that proves you own it.

Design a type for an agent's tool result with this rule enforced by the type system: a result is either a success carrying content: string, or a failure carrying error: string. It must be impossible to build one with both, and impossible to build one with neither.

You have exactly the tools. If you find yourself writing content?: string; error?: string, that's the wrong answer — work out why before you look.

Why optional fields fail, and what to write instead

{ content?: string; error?: string } is one set containing four kinds of value: content-only, error-only, both, and neither. You wanted two. The two illegal states are sitting right there in your set, and every function that touches this type has to check for cases you swore couldn't happen.

What you want is the union of exactly the two legal sets:

type ToolResult =
  | { ok: true;  content: string }
  | { ok: false; error: string };

Two members. Neither has the other's field. {ok: true, error: "x"} is not in the set and will not compile. The count went from four to two, and the two you deleted were exactly the bugs.

That shared ok field is the discriminant — the tag that lets you tell which member you're holding. You've just invented the discriminated union, which is how every message and every event in pi is modelled, and it's rung 2. Notice you didn't need to be taught it. It fell out of counting values.

What you own now

A type is a set of values. extends is ⊆, and assignability is ⊆. Structural typing because membership is shape, not ancestry. More properties means a smaller set, so & grows the field list and | shrinks what you may safely touch. never = ∅ and unknown = 𝕌, with every one of their behaviours derivable. any = not a set, a hole. And all of it erased before the program runs, which is why validation at the boundary needs a schema that exists at runtime.

One idea. Everything else was consequence. If you ever meet a type error you can't explain, translate both sides into sets and ask which subset claim failed — that question has an answer every single time.

Before you go — the honest part

Same warning as last rung, and it applies harder here because this lesson felt tidy. Set diagrams are satisfying to read. That satisfaction is not the same as being able to use the idea when a real error message is shouting at you in a file you didn't write.

The ToolResult exercise is the one that matters. If you reached for optional fields first, that's your Python-shaped instinct — and noticing it is worth more than getting it right immediately.

Cold check for tomorrow. Without notes: why is {name, age} assignable to {name} but not the reverse? Answer it in terms of how many values are in each set, not how many properties. If you reach for properties, the idea hasn't landed yet — reread the Employee reveal and nothing else.

Next — rung 02, Narrowing is set arithmetic. You built a two-member union at the end there and gave it a tag. Now: you're holding a ToolResult and you need the content. TypeScript won't let you touch it — half the values in that set have no such field. So how do you shrink the set at runtime, and how does the compiler follow along while you do it? That's narrowing, and it ends with the trick where the leftover set being empty is what proves you handled all twelve stream events.

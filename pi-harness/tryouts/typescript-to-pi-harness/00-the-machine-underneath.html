The machine underneath

One thread. It must never stop. Everything follows.

Here is a line from pi/packages/agent/src/agent-loop.ts, line 317. It is the line the entire harness turns around: 

for await (const event of response) {
    switch (event.type) {
        case "text_delta": ...

By rung 7 you will have written your own version of it. There are two hard ideas buried in there. event.type — how one variable can be twelve different shapes and the compiler keeps them straight — that's rungs 1 through 4. Today we earn the other one. Today we earn await.

And I want to earn it, not define it. If I just tell you "await pauses until the promise resolves," you'll nod, you'll write working code, and then one day you'll write something that deadlocks or silently runs three times slower than it should, and you won't know why. That happens because the definition was borrowed. So let's go get it.

Start where you're standing

You think in Python. So write me an agent loop in Python. Not a real one — the shape of one. Send a prompt, get a response, run any tools it asked for, go around again.

You'd write this without thinking:

# Python. Obvious. Correct.
def run_agent(prompt):
    messages = [{"role": "user", "content": prompt}]
    while True:
        response = call_llm(messages)          # ← blocks ~4 seconds
        messages.append(response)
        if not response.tool_calls:
            return response
        for call in response.tool_calls:
            result = execute_tool(call)        # ← blocks too
            messages.append(result)

Fourteen lines, and the whole idea is visible at a glance. Look at what makes it readable: response = call_llm(messages). The next line runs after the response has arrived. Reading order is execution order. Your eye goes down the page and time goes forward with it.

That property — reading order equals execution order — is worth more than you think. Hold onto it. In about four minutes we're going to lose it, and then fight to get it back.

The wall

In Python, requests.get(url) blocks. The interpreter sits there, doing nothing, until bytes come back. You've never once thought this was strange, because it isn't. The OS suspends your thread; some other thread runs; eventually yours wakes up. Costs you nothing.

JavaScript has no equivalent. There is no function in the language, and none in Node's standard library, that sends an HTTP request and returns the response. Not a discouraged one. Not a deprecated one. It does not exist.

Why not? Here's the fact the whole language is built on:

A JavaScript program has exactly one thread, and that thread is also the thing running everything else — every timer, every incoming connection, every keystroke. If it stops, the whole program is deaf.

Think about what "blocking" means in a world with one thread. In Python, blocking means "this thread naps, the others carry on." In JavaScript, there are no others. Blocking means the entire program is frozen. Not slow — frozen. During those four seconds waiting on the model, your agent cannot notice that you hit Ctrl-C. It cannot draw a spinner. It cannot accept the message you're typing to steer it. It is a brick.

So the language designers made a choice that sounds extreme and is actually the only coherent one: don't offer the blocking version at all. Take it off the table. If you can't block, you can't accidentally freeze everything.

Being precise, because I said blocking is impossible and it isn't quite. Node does ship fs.readFileSync, and it genuinely blocks. So the rule isn't "blocking is impossible" — it's "blocking is catastrophic, and for the network they simply didn't build the door."

readFileSync survives because a local disk read is under a millisecond, and startup code runs before anything else needs the thread. Use it at startup and nobody is harmed. Use it in your agent loop and you've frozen the program.

You can watch pi apply exactly that rule. Grep it yourself: packages/agent/src — the loop — contains not one readFileSync. Every sync read in the project sits in config, settings, keybindings, auth storage: startup paths, all of them. That's not inconsistency. That's the rule applied correctly in both directions.

See the one thread with your own eyes

I could keep asserting "one thread." Better if you catch it in the act. Here are four lines. setTimeout(fn, 0) means "run fn, zero milliseconds from now." 

console.log("A");
setTimeout(() => console.log("B"), 0);
Promise.resolve().then(() => console.log("C"));
console.log("D");

Write down the output order before you open this. All four letters.

What actually prints 
A
D
C
B

If you guessed A B C D — reading order — that's the Python instinct and it's the right instinct to have had. If you guessed A D B C, you already knew callbacks get deferred, but not the last twist.

Here's what the one thread is doing:

A prints. Then setTimeout is called — it doesn't run the function, it hands it to the runtime and returns instantly. Then .then(...) likewise hands off a function and returns instantly. Then D prints.

Now — and this is the part worth having — your code is finished. The thread has reached the bottom of the file. Only now, with nothing left to run, does it go looking for parked work. And "zero milliseconds" turns out to have meant "after you're done," not "immediately."

C before B because there are two queues, and promise callbacks sit in the higher-priority one. It's drained completely before a single timer fires. You will not need that detail often, but the day two things happen in an order you swear is impossible, it's this.

Sit with that for a second, because it's the whole model. The thread runs your code to completion, without interruption. Then, and only then, it picks up parked work. Then it runs that to completion. Round and round.

That's the event loop. Not a framework, not a library — the shape of the runtime. And notice the deal it strikes: nothing ever interrupts you mid-function, so you never need a mutex, and there are no data races. That's the payment you receive. The price is that you may never, ever stop.

So what can fetch possibly return?

Now we can derive the answer instead of being handed it. The constraint is fixed: fetch(url) must return immediately, because the thread can't wait. But the response won't exist for another four seconds.

Reason it through before reading on. What are the candidates?

It has to return something right now. What could that something be? Try to list the options and kill them yourself. There are only about three.

The candidates, and why two of them die

Return the response. Dead on arrival. It doesn't exist yet. Nothing to return.

Return nothing, and have the result appear somewhere later — a global, a mailbox, an event you subscribe to. This is the one worth taking seriously, because it does work, and it's how a lot of older code was written. It dies on correlation: fire off three requests and three answers land in the mailbox, and nothing connects an answer back to the question that caused it. You've severed cause from effect. Now you're hand-rolling request IDs, which is the runtime's job.

Return a way to be told. Hand fetch a function, and let it call that function when the bytes land. This one survives — cause and effect stay stapled together. It's the callback, and it was the answer for about fifteen years.

So let's take the survivor seriously. Callbacks. Rewrite the agent loop:

function runAgent(prompt, done) {
  const messages = [{ role: "user", content: prompt }];

  callLLM(messages, (err, response) => {
    if (err) return done(err);
    messages.push(response);
    if (!response.toolCalls) return done(null, response);

    executeTool(response.toolCalls[0], (err, result) => {
      if (err) return done(err);
      messages.push(result);

      callLLM(messages, (err, response2) => {
        if (err) return done(err);
        // ... and now go around again. How?
      });
    });
  });
}

Two questions. Answer both before opening.

1. The Python version looped with while True. Where did the loop go? Can you put it back?

2. Count the error checks. What happens to that count as the agent runs twenty turns instead of two?

Why this collapses

The loop is gone and you can't put it back. A while loop needs the body to finish before the next iteration starts. But the body here finishes instantly — it just schedules a callback. So the loop would spin thousands of times, firing thousands of requests, before a single response arrived. To actually iterate you have to make the function call itself from inside its own callback. Your loop has become recursion turned inside out, and it no longer looks anything like "keep going until the model stops asking for tools."

Errors don't propagate, they replicate. In Python one try/except wraps the whole loop, because an exception rides the call stack upward. But by the time a callback runs, the stack that created it is gone — the thread returned to the event loop long ago. There is nothing above you to throw to. So every single callback re-checks and re-forwards the error by hand, and the one you forget is a bug that swallows a failure silently.

And reading order no longer equals execution order. The thing I told you to hold onto. It's gone. Time now runs rightward, into the indentation. Twenty turns of agent is twenty levels deep. This has a name, and people who lived through it don't say it fondly.

So callbacks aren't wrong, exactly. They're correct and unusable, which is a specific and interesting kind of failure. Something is structurally off. Let's find it.

The thing that was missing

Look hard at the callback signature:

callLLM(messages, (err, response) => { ... })

callLLM returns nothing. The pending work — a real thing, running right now, that will eventually produce a value or fail — has no representation in your program. You can't name it. You can't hold it. You can't put it in a list, or return it from a function, or pass it to something else.

That's the actual defect. Not the nesting; the nesting is a symptom. The defect is that the most important thing in the program is invisible to the program.

So fix that, and see what falls out.

Suppose callLLM(messages) did return something. It can't be the response. But what's the next best thing it could hand you — something that exists right now, and that has a useful relationship to a value that doesn't exist yet?

The move

A box. An object that exists immediately, is empty, and is wired up so that when the bytes arrive, they get put inside it.

It exists now, so you can name it, store it, return it, put it in an array. It's empty now, so it isn't lying about having the answer. And it carries a promise about the future: something will land in here — a value, or an error — exactly once.

That box is the whole idea. In JavaScript it's called a Promise.

You cannot block. So a value that isn't here yet has to become a value that is here now — a box that will contain it. The box is the Promise.

I want to be exact about what just happened, because it's the move worth stealing, not the noun. We took something that lived only in the runtime's head — pending work — and made it a first-class value in the language. Turning an implicit process into an explicit value. Once you've done that, everything you can do to values, you can now do to work-in-progress.

Watch how much you get back for free:

// It's a value, so you can name it.
const pending = callLLM(messages);

// It's a value, so you can put it in an array.
const three = [callLLM(a), callLLM(b), callLLM(c)];

// It's a value, so you can write functions that combine them.
const all  = await Promise.all(three);   // all three, concurrently
const first = await Promise.race(three); // whichever wins

Compare that to threads. Concurrency in the callback world meant counters and shared mutable state and getting it wrong. Here "run these three at once and wake me when they're all done" is a function that takes an array, because the pending operations are ordinary values in an ordinary array. That's not a library being clever. That's what reification buys you.

Now await is obvious

We have boxes. But if writing code with boxes still meant .then(fn) chains, we'd have traded deep nesting for long chains and only half-won. We still haven't got back the thing we lost: reading order equals execution order.

await is that, and it means exactly one thing:

Give me the value in this box. Until it arrives, hand the thread back to the event loop — let it run timers, other requests, keystrokes. When the box fills, resume me right here.

Which lets us write the loop we actually wanted. Here is the Python from the top of this page, and the JavaScript, side by side: 

# Python                          // JavaScript
def run_agent(prompt):                async function runAgent(prompt) {
  messages = [...]                      const messages = [...];
  while True:                           while (true) {
    r = call_llm(messages)                const r = await callLLM(messages);
    messages.append(r)                    messages.push(r);
    if not r.tool_calls:                  if (!r.toolCalls) return r;
      return r                            for (const c of r.toolCalls) {
    for c in r.tool_calls:                  const out = await execTool(c);
      out = execute_tool(c)                 messages.push(out);
      messages.append(out)                }
                                        }
                                      }

The while (true) is back. The reading order is back. One try/catch around the whole thing would work, because await turns a rejected box into a thrown exception right at that line. The structure is the Python structure. Six extra characters, twice.

But underneath, that function is shredded — chopped at every await into pieces the event loop runs at different times, minutes apart, with thousands of other things happening in between. The compiler is doing the callback rewrite for you, and doing it perfectly.

async on the front is the honest half of the bargain. It declares: this function contains suspension points, so it cannot hand you a real value — it hands you a box. Every async function returns a Promise. Always, even if the body just returns 3. It has no choice; it returned to the caller long before it finished.

The misconception that will bite you

Everyone gets here and concludes: async means parallel. It does not. There is still exactly one thread. Nothing in this lesson added a second one.

Concurrency is having many things in flight. Parallelism is having many things executing at the same instant. JavaScript gives you the first and not the second — and for an agent harness the first is all you ever wanted, because you're not computing anything. You're waiting on a model in a datacenter. Waiting parallelises beautifully on one thread; waiting is free.

The trap is that this distinction is invisible until it costs you 3× and you can't see why. So let's make you feel it rather than believe it.

Your turn — and this one you actually run.

Put this in t.js and run node t.js. Node 18 or newer; check with node -v. 

const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

async function fakeLLM(prompt) {
  await sleep(500);              // pretend: a model, thinking
  return `echo: ${prompt}`;
}

async function main() {
  // --- version A: one after another
  let t = Date.now();
  const a1 = await fakeLLM("one");
  const a2 = await fakeLLM("two");
  const a3 = await fakeLLM("three");
  console.log("sequential:", Date.now() - t, "ms");

  // --- version B: all in flight, then wait
  t = Date.now();
  const boxes = [fakeLLM("one"), fakeLLM("two"), fakeLLM("three")];
  const results = await Promise.all(boxes);
  console.log("concurrent:", Date.now() - t, "ms");
}

main();

Predict both numbers before running. Then run it.

Then the question that matters: one thread, no parallelism — so where did the time go? Version B isn't doing more at once. Say precisely what's different.

What you saw, and why

Roughly 1500 ms and 500 ms.

The difference is when the work starts, and it's decided by where you put await — not by any parallelism.

In version A, await on line one means the thread doesn't reach line two for half a second. The second call hasn't started. Three naps, back to back.

In version B, look at the array literal. fakeLLM("one"), fakeLLM("two"), fakeLLM("three") — all three called, with no await between them. Each runs until it hits its own internal await sleep, parks itself, and hands back a box. All three timers are now ticking down together. Three boxes in an array. Then you wait, once.

So the rule, and it's the one that separates people who use await from people who understand it: calling an async function starts the work. await only decides where you stop to collect it. An await placed one line too early costs you all your concurrency, silently, with no error and no warning. It just gets slower.

And note the thread was idle for essentially the entire 500 ms in both versions. It wasn't working harder in B. It was waiting smarter.

You've met this before, and it's worth naming. Python's asyncio is the same design: one thread, an event loop, await, and asyncio.gather where JavaScript writes Promise.all. If you've written async def, you already owned this model — you just owned it as one option among several.

That's the real difference, and it's cultural, not technical. In Python, async is a dialect. Most libraries are blocking; you choose to opt in; requests and httpx both exist. In JavaScript there was never a choice, so everything is async — every file read, every socket, every library, all of it, all the way down. Nothing to opt into, nothing to bridge, no colour problem to manage. The constraint that looked like poverty turns out to have bought uniformity.

Three things to notice yourself before I point at them.

1. Why is fetching the API key awaited? It's just a string.

2. There's a signal being passed down. Given that this thread must never block — what do you think it's for, and why can't you just kill the request the way you'd kill a thread?

3. for await. You know await now — one box, one value. What must for await be waiting on, over and over?

What each one is telling you

1. The key might not be a string yet. pi's own comment says it: "important for expiring tokens." With OAuth providers the token can expire during a long tool run, so fetching it may mean a network round-trip to refresh. Might be instant, might take a second. Since it can be slow, it must be a box — and once any layer of a stack is async, everything above it is too. This is the uniformity from the aside, arriving as a real consequence.

2. signal is how you cancel without threads. You can't kill this operation from outside — there's no other thread to kill it from, and nothing interrupts running code. So cancellation has to be cooperative: you hand the operation an object it can check, and when you flip it, the operation notices at its next suspension point and tidies up. Every "stop" button in every agent is this. When you hit Escape in pi mid-response, that's a signal being flipped — and the reason the UI could hear your keypress at all is that the thread was never blocked.

3. for await is a sequence of boxes, not one box. The model doesn't hand you a response; it dribbles it out over seconds — a token, a token, a tool call. That's not one not-yet, it's hundreds, in order, ending eventually. One Promise can't express that: a box fills exactly once. So there's a second construct for many-not-yets-in-order, and that's rung 5. You've now met the exact problem it exists to solve, which is the right way to arrive at it.

What you own now

One thread, which must never stop. Therefore no blocking. Therefore a value that isn't here yet must be reified as a value that is here now — a Promise. Therefore await, which suspends you and frees the thread. Therefore async, which is the admission that this function returns a box.

That's one idea with four consequences, not five facts. If you can walk that chain forward from "one thread" without looking, you have it. If you can only recite the end of it, you don't yet.
